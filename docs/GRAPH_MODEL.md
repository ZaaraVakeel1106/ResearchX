# Research X — Graph Model

**Status:** Proposed design
**Product:** Research X
**Purpose:** Define how papers, citations, similarity, research relationships, and evidence are represented and explored.

## 1. Purpose

The Research X graph helps users understand how academic papers connect.

It should support questions such as:

- Which papers does this paper cite?
- Which later papers cite it?
- Which papers are closely related to my research question?
- Which papers introduced an idea, extended it, challenged it, or evaluated it?
- How did a particular concept develop across publications?
- Which references should I read next, and why?
- What evidence supports a proposed relationship between two papers?

The graph must help users explore research without presenting uncertain relationships as established facts.

## 2. Core Design Principle

**Every relationship must have a clearly defined type and provenance.**

Research X must distinguish at least three categories:

1. **Bibliographic relationships:** supported by explicit reference or citation data.
2. **Similarity relationships:** based on a documented similarity method, such as text embeddings or shared metadata.
3. **Inferred research relationships:** interpretations generated by a model or analysis workflow, such as a paper extending, challenging, or applying another paper.

These categories must never be visually or semantically interchangeable.

A direct citation proves that a reference relationship was recorded. It does not, by itself, prove that the citing paper agrees with, validates, or builds upon the cited work.

## 3. Graph Entities

### 3.1 Paper Nodes

Each paper node represents one canonical paper record.

A node may expose:

- Internal paper ID.
- Title.
- Publication year, when known.
- Authors.
- Venue, when known.
- DOI or another verified external identifier.
- Abstract availability.
- Open-access availability, when reliably established.
- Citation and reference counts, with their source and interpretation.
- Whether the paper is saved in the current workspace.

The graph should not require every field to be present. Missing metadata must be displayed honestly.

### 3.2 Citation Edges

A citation edge represents an explicit bibliographic relationship.

Direction:

`Citing paper → Cited paper`

For example, if Paper A cites Paper B, the directed edge is A → B.

Each citation edge should preserve:

- Citing paper ID.
- Cited paper ID, if resolved.
- Source provider or reference record.
- Resolution status.
- Retrieval or observation timestamp where available.

An unresolved reference should remain an unresolved reference record. It must not be converted into a guessed paper node or a verified citation edge.

### 3.3 Similarity Edges

A similarity edge connects papers considered related by a defined similarity method.

Potential methods include:

- Abstract or full-text embedding similarity.
- Shared references.
- Shared authors or venues.
- Keyword or topic overlap.
- Bibliographic coupling.
- Co-citation.

These methods have different meanings and should not be collapsed into one unexplained score.

Where available, store:

- Method name and version.
- Input fields or representations used.
- Similarity score.
- Score interpretation.
- Computation timestamp.
- Relevant limitations.

A similarity score is not automatically a probability that two papers are relevant or scientifically equivalent.

### 3.4 Inferred Research-Relationship Edges

These edges represent interpretations that may help a researcher navigate the literature.

The canonical top-level relationship types are `CITES`, `SIMILAR_TO`, and `INFERRED_RELATED_TO`, matching `ARCHITECTURE.md`. The labels listed below are proposed subtypes of `INFERRED_RELATED_TO`, not separate verified citation types. They must only be used when the system has a documented method for producing and validating the corresponding inference.

Candidate relationship types include:

- `extends`
- `replicates`
- `evaluates`
- `challenges`
- `contradicts`
- `applies`
- `surveys`
- `uses_method_from`
- `compares_with`
- `related_to`

These are proposed labels, not guaranteed classifications.

Every inferred relationship must include, where available:

- Source paper.
- Target paper.
- Relationship type.
- Short explanation.
- Supporting or contradicting evidence.
- Evidence locator or source reference.
- Model or method version.
- Confidence information, if meaningfully calibrated.
- Generation timestamp.

The UI must label these relationships as inferred. If adequate evidence is unavailable, Research X should omit the relationship or mark it as uncertain instead of inventing support.

## 4. Core Graph Queries

The initial graph should support these operations.

### 4.1 References

Given a paper, return papers it cites.

- Follow outgoing citation edges.
- Include resolved references by default.
- Optionally show unresolved references separately.
- Preserve source provenance.

### 4.2 Citing Papers

Given a paper, return papers that cite it.

- Find incoming citation edges.
- Apply documented filters.
- Make it clear that the results depend on the coverage and freshness of the underlying provider.

### 4.3 Related Papers

Given a paper, return related papers ranked using a documented method.

The response must explain whether ranking uses citation proximity, similarity, shared references, or inferred relationships.

Do not combine different signals into an opaque score without defining the scoring method and its limitations.

### 4.4 Bounded Neighborhood

Return a local neighborhood around a selected paper.

The query should support:

- A configurable depth.
- A maximum node count.
- Relationship-type filters.
- Publication-year filters where useful.
- Optional exclusion of already displayed nodes.
- Deterministic limits and ordering where practical.

The initial implementation should use small neighborhoods rather than loading an entire citation network.

### 4.5 Path Exploration

A later feature may show paths connecting two papers.

Each path must explain what its edges represent. A path made entirely of citations means something different from a path that includes similarity or AI-inferred edges.

Do not imply that a graph path establishes scientific causation or direct intellectual influence.

## 5. Graph Response Contract

The graph API should return a structured node-and-edge representation.

Conceptual example:

```json
{
  "root_paper_id": "paper-uuid",
  "nodes": [
    {
      "id": "paper-uuid",
      "title": "Example Research Paper",
      "year": 2025,
      "metadata_status": "available"
    }
  ],
  "edges": [
    {
      "id": "edge-id",
      "source": "paper-uuid",
      "target": "another-paper-uuid",
      "type": "CITES",
      "origin": "provider",
      "evidence_available": true
    }
  ],
  "truncated": false,
  "next_cursor": null
}
```

This example is illustrative, not a final API contract. Exact fields, enums, pagination behavior, and error responses must be finalized in `docs/API_SPEC.md`.

Requirements:

- Node IDs must be stable within the application's canonical data model.
- Every edge endpoint must refer to a node included in the response, unless the API explicitly models external or unresolved targets.
- Every edge must have a documented type and direction.
- The response must indicate when results have been truncated.
- Do not fabricate publication years, scores, evidence, or metadata status.
- The graph must be safe to render when some metadata is missing.

## 6. Graph Layout and Interaction

The frontend will initially use Cytoscape.js, subject to validation during implementation.

Core interactions:

- Select a paper node to open its details.
- Expand its references or citing papers.
- Expand related papers separately from citations.
- Filter relationship types.
- Filter by publication year where useful.
- Search within currently loaded nodes.
- Highlight the selected node and its immediate neighbors.
- Reset or recenter the view.
- Show a legend explaining edge types.
- Show a clear loading, empty, and error state.
- Prevent repeated expansion from creating duplicate nodes or edges.
- Keep the graph usable on smaller screens and with keyboard interaction.

The interface must not rely on color alone to distinguish relationships. Use labels, line styles, icons, or a details panel as appropriate.

## 7. Graph Exploration Experience

The graph should guide the user through research instead of presenting an overwhelming network.

A recommended initial workflow:

1. The user opens a paper.
2. Research X displays a small citation neighborhood.
3. The user chooses whether to explore references, citing papers, or related work.
4. The graph expands only in the selected direction or relationship category.
5. Selecting a node reveals a concise metadata panel.
6. The user can open the paper, inspect its references, view available evidence, or save it to a workspace.
7. The user can return to the previous exploration state.

The graph should communicate why a paper is shown. For example: “Cited by this paper,” “Shares several references,” or “Semantically similar abstracts.” Avoid generic labels such as “connected” when the actual relationship is known.

## 8. Ranking and Discovery

Potential ranking signals include:

- Direct citation relationship.
- Shortest citation distance.
- Similarity score from a defined method.
- Relevance to the user's search query.
- Publication date.
- User-selected criteria.

Ranking must not equate citation count with research quality. Citation counts vary by field, age, provider coverage, and publication type.

The initial release should favor transparent rules over complex ranking models. If multiple signals are combined, document their relative contribution and allow the UI to explain the ranking.

## 9. Performance and Data Quality

- Limit nodes and edges returned by each request.
- Use pagination or expansion requests for large neighborhoods.
- Avoid repeatedly fetching the same unchanged graph data unnecessarily.
- Index citation endpoints and frequently queried relationship fields.
- Deduplicate edges using stable identity and relationship-specific constraints.
- Preserve direction for citations.
- Handle cycles in citation traversal safely.
- Validate all relationship types against documented schemas.
- Track source coverage and retrieval timestamps where possible.
- Test empty graphs, disconnected nodes, unresolved references, cycles, duplicate records, and large neighborhoods.

Do not introduce a dedicated graph database before benchmarks show that PostgreSQL is insufficient for the initial workload.

## 10. Trust, Evidence, and Limitations

Research X must communicate the limitations of graph data.

- Missing edges do not prove that no relationship exists.
- Citation coverage may be incomplete or delayed.
- Similarity does not prove agreement, influence, or correctness.
- Co-citation and shared references indicate bibliographic patterns, not necessarily conceptual equivalence.
- AI-inferred relationships are hypotheses unless independently supported.
- Citation counts must be associated with a source and, where available, an observation date.
- A citation edge alone does not establish that the cited work supports a particular claim.

When a relationship has supporting evidence, users should be able to inspect that evidence and navigate to its source.

## 11. Privacy and Access Control

- Public bibliographic graph data may be shared according to the relevant provider's terms.
- Private notes, workspace membership, and user-uploaded documents must not become public graph data by default.
- Graph endpoints must not expose private workspace data to unauthorized users.
- AI-inferred relationships based on private documents must respect the privacy and access rules of those documents.
- Apply authorization on the backend before returning user-specific graph information.

## 12. Testing Requirements

The implementation must test:

- Citation direction.
- Incoming and outgoing citation queries.
- Unresolved references.
- Duplicate-edge prevention.
- Relationship-type filtering.
- Bounded traversal and maximum node counts.
- Cycle handling.
- Pagination or truncation behavior.
- Missing metadata.
- Stable node identity.
- Correct labeling of provider-backed and inferred edges.
- Evidence linkage for inferred relationships.
- Authorization for private workspace information.

## 13. Decisions Still Required

Before graph implementation, document:

1. The initial provider's actual citation and reference coverage.
2. The exact graph API response schema.
3. Initial node and edge limits.
4. Whether similarity edges are included in the first release.
5. Whether inferred research-relationship edges are deferred until evidence retrieval is reliable.
6. The initial ranking method for related papers.
7. The caching strategy and freshness expectations.
8. The graph's keyboard-accessibility and small-screen behavior.
9. Which citation and relationship queries need database indexes.
10. What evidence must be available before an inferred edge is displayed.

## 14. Acceptance Criteria

The graph model is ready to guide implementation when:

- Citation direction is unambiguous.
- Citation, similarity, and inferred relationships remain distinct.
- Edge provenance and uncertainty are represented.
- Unresolved references are handled honestly.
- Graph queries have bounded, testable behavior.
- The frontend can render partial or missing metadata safely.
- Users can inspect why papers are connected.
- Privacy rules apply to all workspace-specific information.
